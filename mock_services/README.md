# Mock Services Architecture

This folder contains a small microservice-style demo system used to generate realistic service-to-service traffic, latency, and occasional failures for observability demos.

## High-level topology

- **k6** (on the host) sends requests to `gateway`.
- `gateway` calls:
  - `auth-service` (always)
  - `product-service` (always)
  - `order-service` (about 70% of requests)
- `product-service` calls `inventory-service`.
- `order-service` calls `inventory-service` and `payment-service` (with retry).

Traffic fans out from gateway to downstream services, creating edge activity and concurrent open connections visible in the dhrishti graph.

## Running the stack

```bash
cd mock_services
docker compose up --build
```

Gateway is exposed on `http://localhost:8080/`.

## Generating load with k6

Load is no longer generated by an in-compose Python client. Use k6 instead — see [`k6/README.md`](k6/README.md).

Quick start:

```bash
cd mock_services/k6
k6 run load.js

# Or run a full benchmark against dhrishti
./benchmark.sh
```

## Services and behavior

### `gateway`

- Entry point: `GET /`
- Sequentially fetches downstream data and returns aggregated JSON
- Per-service timeouts: auth 5s, product 8s, order 15s

### `auth-service`

- `GET /auth` — simulated latency ~0.12–0.45s (occasional spikes)

### `product-service`

- `GET /product` — calls `inventory-service`

### `inventory-service`

- `GET /inventory` — bimodal latency, ~8% HTTP 500

### `order-service`

- `GET /order` — calls inventory + payment (with retry)

### `payment-service`

- `GET /pay` — mixed latency, ~10% HTTP 500

## Legacy client

The Python client in `client/` is kept for reference but removed from `docker-compose.yml`. Use k6 for configurable, production-style load testing.
